# Frontend ↔ Backend protocol

Single source of truth for the WebSocket contract between the Next.js dashboard
(`frontend/`) and the Python forensic backend (`vanirakshak-backend/`).

- **Endpoint:** `ws://<host>:8000/ws/stream` (alias of `/v1/stream`, `/api/v1/stream`)
- **Audio:** mono, 16-bit signed little-endian PCM, 16 000 Hz
- **Framing:** one JSON text handshake, then binary PCM frames

## 1. Handshake (required, must be first)

The server calls `ws.receive_text()` before reading any audio. If the first
frame is binary, `json.loads` fails and the socket is closed with **1003**.
The client must therefore send this *before* starting the microphone:

```json
{
  "session_id": "r5-demo-1699999999999",
  "sample_rate": 16000,
  "caller_id": "",
  "claimed_identity": "",
  "transaction_value_inr": 0,
  "origin_country": "IN",
  "prior_fraud_score": 0
}
```

All fields are optional except `sample_rate`; unset values fall back to the
defaults above. `session_id` is generated by the server when omitted.

**`claimed_identity` fallback:** when omitted (or `""`), the server does not
simply skip ASV — it falls back to the identity of whichever anchor is loaded
(`GET /api/v1/health`'s `anchor.user_id`), so speaker verification runs by
default with the one enrolled voice this system currently ships. This applies
to the WS handshake, `POST /v1/sessions`, and `POST /analyze`'s form field
alike (`server/app.py::_resolve_claimed_identity`). An explicit
`claimed_identity` the caller sends is never overridden. See `metrics.asv_evaluated`
below for how to tell whether ASV actually ran for a given window.

## 2. Audio frames

Binary messages, each an `Int16Array` at `sample_rate`. The browser captures at
16 kHz via an AudioWorklet (`frontend/public/worklets/pcm-capture.js`), which
posts float32 blocks that the client converts to int16 before sending.

**Known gap:** the client requests `sample_rate: 16000` on `getUserMedia` and
the `AudioContext` constructor, but never resamples if a browser honors a
different hardware rate. There is no resampling on the wire — `sample_rate` in
the handshake is trusted as the truth about what follows it, not verified.

## 3. Verdict messages (server → client)

Emitted once per analysis window (4.04 s sliding window, 1.0 s hop).

```json
{
  "timestamp_ms": 1699999999999,
  "risk_score": 43.2,
  "p_spoof": 0.55,
  "tier": "CHALLENGE",
  "metrics": {
    "cm_score": 0.61,
    "cm_genuine_prob": 0.39,
    "asv_consistency": 0.68,
    "asv_evaluated": true,
    "channel_anomaly": 0.12,
    "prosody_unnatural": 0.3,
    "snr_db": 18.4,
    "codec_guess": "wideband"
  },
  "trigger_challenge": true,
  "interlock_active": false,
  "receipt_hash": "9f2c…",
  "challenge": {
    "phrase": "mango, 8, nadi, 4.",
    "expected_digits": ["8", "4"],
    "expected_full": "mango 8 nadi 4",
    "instructions": "Now repeat ONLY the digits, in order, quickly.",
    "issued_at_ms": 1699999999999,
    "seed": 42
  },
  "semantic": {
    "available": false,
    "transcript": "",
    "hinglish_text": "",
    "language": null,
    "matches": [],
    "categories_hit": [],
    "semantic_risk": 0.0,
    "keyword_risk": 0.0,
    "claim_risk": 0.0,
    "claim_findings": [],
    "provider": null,
    "reason": "not started"
  }
}
```

`challenge` is `null` unless a challenge is active. `semantic` is **always**
present — see §3.1 for its populated shape once ASR actually runs.

**`metrics.asv_evaluated`** (bool): whether ASV ran a real biometric
comparison for this window (`asv.consistency_score`'s `is_enrolled` result).
When `false`, `asv_consistency` is the fusion-neutral placeholder `0.5`, not a
measured similarity — this happens when the claimed identity (after the
handshake fallback above) isn't enrolled, or the anchor failed to load
(`health.anchor.error`). A client must not render `asv_consistency` as a
confidence score without checking this flag first.

**`challenge` field notes:**
- `phrase` is comma-delimited word/digit tokens ending in a period, e.g.
  `"mango, 8, nadi, 4."` — not prefixed with `"Say:"`.
- `expected_digits` is a `List[str]`, one character each.
- `expected_full` is the full spoken phrase as space-separated tokens (words
  *and* digits, e.g. `"mango 8 nadi 4"`) — not the digits alone.
- `instructions` is always `"Now repeat ONLY the digits, in order, quickly."`
  The caller is asked to repeat only the digits; grading only checks digit
  order plus response latency, never the words.

**Challenge outcomes and the interlock — current behavior, open for revision:**
Every graded challenge (`POST /v1/sessions/{id}/challenge`) is now recorded in
the audit chain (`challenge_passed`, `challenge_confidence`,
`response_latency_ms` features). A **failed** challenge always escalates the
session to `BLOCK`, permanently, for the rest of the call. A **passed**
challenge, as shipped today, does **not** clear a prior `BLOCK` and does not
allow a second challenge to fire later in the same session — `_blocked` and
the one-challenge-per-session gate are both one-way. This is a real product
decision, not settled: `vanirakshak-backend/vanirakshak/session.py`'s
`grade_challenge()` carries a `TODO(human)` marking exactly this — whether a
pass should be a genuine recovery path (un-blocking the call and re-arming a
future challenge) instead. **Do not build client logic that assumes a pass
un-blocks the interlock** until that TODO is resolved and this section is
updated to match.

### 3.1 `semantic` — parallel ASR + keyword context signal (advisory)

Populated shape once transcription succeeds:

```json
{
  "available": true,
  "transcript": "aapka bank account KYC ke liye turant OTP bhejiye",
  "hinglish_text": "aapka bank account KYC ke liye turant OTP bhejiye",
  "language": "hi",
  "matches": [
    {"category": "otp_pin_exfiltration", "term": "otp"},
    {"category": "kyc_account_threat", "term": "kyc"},
    {"category": "kyc_account_threat", "term": "bank"},
    {"category": "urgency_pressure", "term": "turant"}
  ],
  "categories_hit": ["kyc_account_threat", "otp_pin_exfiltration", "urgency_pressure"],
  "semantic_risk": 0.95,
  "keyword_risk": 0.95,
  "claim_risk": 0.95,
  "claim_findings": [
    {
      "rule_id": "otp_request",
      "claim": "Caller is asking you to share an OTP / PIN / CVV.",
      "finding": "No bank, wallet, or government body ever asks for an OTP, PIN, or CVV — on any channel, for any reason. A request for one is fraudulent by definition, regardless of who the caller claims to be.",
      "authority": "RBI customer-protection guidance; every major Indian bank's published security policy",
      "severity": 0.95,
      "matched_terms": ["otp", "bhejiye"]
    }
  ],
  "provider": "groq",
  "reason": null
}
```

The **key set is identical** whether `semantic` is idle (nothing transcribed
yet), degraded (`available: false`, ASR unavailable or errored), or populated
— all three carry the same twelve keys shown above. This is deliberate and
regression-tested (`scripts/integration_check.py`'s
`"semantic block has the full key set on every verdict"` check): a client
should never need to branch on which keys exist, only on `available` and the
risk/finding values.

Two independent readings of the same transcript:

| Field | Question it answers | Method |
|---|---|---|
| `keyword_risk` | "Does this call use scam *vocabulary*?" | Bag-of-words over `semantic/keywords.py` categories |
| `claim_risk` | "Did the caller *demand something that contradicts published policy*?" | Rule match over `semantic/claims.py`, each finding citable to an authority |

`semantic_risk` is `max(keyword_risk, claim_risk)` — the value actually fused
into the risk score. Max rather than sum: a confirmed OTP request is already
decisive alone, and summing would let stacked weak vocabulary outweigh it.

`claim_findings` is the useful half for an operator. A keyword chip means "this
word occurred"; a finding means "the caller demanded something that contradicts
a published rule", and names the rule and who published it. This distinction
removes a real false-positive class: *"I received an OTP from the bank earlier"*
scores `keyword_risk` 0.75 but `claim_risk` 0.0, because no demand was made.

**Scope, stated honestly:** this is rule-based verification against a curated
knowledge base — not open-ended fact-checking. It cannot verify case-specific
assertions ("your balance is ₹5,000", "I'm from the Andheri branch); those need
live data the system does not have. It verifies the categorical class of claim
scam scripts structurally depend on, where the contradiction holds regardless of
caller or account.

Produced by `vanirakshak/semantic/` (Groq Whisper transcription of the same
4.04 s window the acoustic detectors score, then a scam-phrase keyword
scorer over the transcript). **This is a parallel, advisory context signal —
not a detector.** The acoustic pipeline (CM/ASV/channel/prosody → Bayesian
fusion) remains the sole authority for `risk_score`/`tier`; `semantic_risk`
only contributes one small additive term to the fusion (`VR_FUSION_W_SEMANTIC`,
default `0.4`, versus `2.4` for the CM anti-spoofing term). This system does
not do open-ended transcript-first/LLM-RAG fact-checking — see
`docs/FLOWCHARTS_CORRECTED.md` for the boundary between what this signal does
(scam-vocabulary and known-claim matching) and what it deliberately does not
do (verifying arbitrary factual assertions).

**Timing:**
- On `POST /analyze`: the whole clip is transcribed once, up front, and its
  `semantic_risk` is fed into **every** window's fusion pass — a one-shot
  upload has one transcript for the whole file, so there is no reason to
  re-run ASR per window.
- On `WS /ws/stream`: transcription is a blocking network call and runs off
  the event loop, so it necessarily lands **one window later** than the
  acoustic metrics for the same timestamp — treat `semantic` as "most recent
  transcript available," not perfectly time-aligned with `metrics`.

Degrades to `{"available": false, "semantic_risk": 0.0, ...}` whenever the
optional ASR stack (`torch`, the `groq` package, or `GROQ_API_KEY`) is absent
— the socket, the acoustic verdict, and every other field are unaffected.

## 4. Field mapping

The backend's names predate the dashboard, so the normalization is done inline in `ws.onmessage` in `frontend/app/page.tsx`.

| Dashboard (`AnalysisResult`) | Backend payload |
|---|---|
| `risk_score` | `risk_score` |
| `action` | `tier` |
| `spoof_score` | `p_spoof` |
| `speaker_similarity` | `metrics.asv_consistency` (check `metrics.asv_evaluated` first) |
| `snr_db` | `metrics.snr_db` |
| `challenge_phrase` | `challenge.phrase` |
| `interlock_active` | `interlock_active` |

## 5. Interlock authority

`transactionLocked` is `interlock_active || action === "BLOCK" || risk >= 70`.

**The server is the sole authority** over `tier`/`interlock_active` whenever a
live stream is running (`AGENTS.md` §2). The client does not derive its own
tier from `risk_score` while a WS session is active — it trusts whatever
`tier` the most recent verdict carries, including after a challenge is
graded. `frontend/app/page.tsx`'s `effectiveTier` only substitutes a
locally-derived tier in the two cases where there is no live server verdict
to trust: a manual challenge drill (`docs/PROTOCOL.md` never sees this — no
server challenge exists to track), or the backend being unreachable. This was
previously a real bug (a passed challenge permanently pinned the client to
`ALLOW` regardless of what the server said afterward) — fixed, and the local
thresholds now exist *only* for that stated demo carve-out, not as a general
fallback while a live session is running.

## 6. Reconnect

On `onclose` the client retries unless the close was deliberate
(`manualCloseRef`). Policy: **5 attempts**, exponential backoff —
1 s → 2 s → 4 s → 8 s → 15 s (cap), each with random jitter. After
`MAX_RECONNECT_ATTEMPTS` the client gives up, logs the failure, and requires a
manual restart.

A reconnect starts a **new session**: the server has already discarded the old
call state, so the client must re-send the handshake exactly as in §1 before
streaming audio again. Do not resume mid-stream.

## 7. Alerting (server → webhook)

When a verdict has `trigger_challenge` or `interlock_active`, the backend POSTs
an alert via `vanirakshak/alerts/`. This is server-side on purpose — the browser
must never hold gateway credentials, and a client-reported interlock can be
forged. Not part of the socket contract; the client only ever *displays* the
alert payload it already received.

## 8. Environment

| Variable | Default | Purpose |
|---|---|---|
| `NEXT_PUBLIC_BACKEND_WS` | `ws://localhost:8000/ws/stream` | Dashboard → backend socket |
| `VR_PORT` | `8000` | Backend listen port |
| `VR_HOST` | `127.0.0.1` | Backend bind host |
| `VR_CORS_ORIGINS` | `http://localhost:3001,http://127.0.0.1:3001` | Browser origins allowed by CORS |
| `VR_ALERT_WEBHOOK_URL` | *(unset)* | Alert webhook target; unset disables dispatch |
| `VR_FUSION_W_SEMANTIC` | `0.4` | Fusion weight for the ASR/keyword `semantic_risk` term (§3.1) |
| `GROQ_API_KEY` | *(unset)* | Enables the `semantic` block; unset degrades it to `available: false` (see `requirements-asr.txt`) |
| `VR_ASV_BACKEND` | `stub` | `ecapa` swaps in real ECAPA-TDNN embeddings (`asv_ecapa.py`); changes the `metrics` distribution and the anchor file loaded (`data/anchor_asv_embedding_ecapa.json`) |
| `VR_CM_BACKEND` | `stub` | `wavlm` swaps in real self-supervised features (`cm_wavlm.py`) for the countermeasure score |
| `VR_IMPOSTOR_BLOCK_BELOW` | `0.10` | A **deterministic tier override**: when `metrics.asv_consistency` falls below this, `tier` is forced to `"BLOCK"` regardless of `risk_score` (`risk/fusion.py`'s impostor override). A client deriving its own tier from `risk_score` alone will disagree with the server in exactly this case — see §5 on why the client shouldn't be doing that anyway. |
| `VR_ANCHOR_EMBEDDING` | *(backend-default path)* | Overrides which anchor JSON is loaded, bypassing the `VR_ASV_BACKEND`-keyed default |
| `VR_FUSION_PRESET` | *(unset)* | `demo` applies a preset fusion-weight override tuned for the shipped demo clips |

## 9. Conformance test

`vanirakshak-backend/tests/test_stream_e2e.py` replays exactly what the
dashboard does — handshake, then int16 PCM — and asserts that every verdict
carries `risk_score`, `p_spoof`, `tier`, `metrics`, `interlock_active` plus
`metrics.asv_consistency` and `metrics.snr_db`.

`scripts/integration_check.py` goes further: it replays `demo_04_impostor.wav`
over a real WS socket and additionally asserts `metrics.asv_evaluated`
presence, the full `semantic` key set across idle/degraded/populated shapes,
the complete `challenge` object shape (including the `expected_full` fix
above), and that the `VR_IMPOSTOR_BLOCK_BELOW` override actually holds across
every verdict in the stream. Run either after changing any part of this
contract:

```bash
pytest vanirakshak-backend/tests/test_stream_e2e.py
python scripts/integration_check.py
```
